# Версионирование

Постановки UI-задач должны требовать аудит, понятные исправления и характерные проверки, без обязательных числовых метрик, профилирования и полного обхода экранов. Декоративные пульсации, тени и свечения удаляются по решению пользователя; замеры не являются условием удаления.

Правила работы с интерфейсом находятся в [docs/ui/README.md](docs/ui/README.md). Результат и проверку описывай в сообщении коммита и в комментарии при закрытии issue.

Все задачи «Династии», включая клиентские, веди в [Issues серверного репозитория](https://github.com/Planetary-Annihilation-Fandom/pa.dynastiya.server/issues).

У каждого автора есть постоянная ветка `dev-<логин>`. Создай её от актуального `dev` при первом использовании. Для каждой задачи создай отдельную ветку от `dev-<логин>` и после согласования влей её в ветку автора. Для переноса изменений в общий `dev` открывай PR из `dev-<логин>`.

Создавай коммиты, отправляй изменения в `origin` и открывай pull request только с явного разрешения пользователя на соответствующие действия. Просьба выполнить задачу разрешает подготовить изменения локально.

Любое слияние веток, включая fast-forward, требует явного разрешения пользователя. В `dev` и `main` используй pull request с merge-коммитом. Прямое слияние выполняй по явному указанию пользователя влить изменения без PR. При открытии PR запроси ревью у всех коллабораторов-людей с правом записи, кроме автора, и дождись одобрения каждого перед слиянием.

Зависимости из строки «Нужно до начала работ» должны быть влиты в `dev` соответствующего репозитория. Выпуск идёт через PR из `dev` в `main` с обновлёнными `version` и `date` в `modinfo.json` изменённой части. После слияния поставь тег, а для синхронизации `dev` используй отдельный PR из `main`. Порядок работы описан в [руководстве](docs/publishing.md).

Версии клиентской и серверной частей ведутся независимо в их `modinfo.json` по схеме `x.y.z`: `x` повышается при существенном нарушении совместимости, `y` — при необходимости миграции сохранённых данных, `z` — при остальных изменениях. Подготовь новую версию и дату в отдельной ветке от `dev-<логин>` и внеси их в `dev` до слияния релизного PR. Прямое указание пользователя повысить версию сейчас имеет приоритет.
