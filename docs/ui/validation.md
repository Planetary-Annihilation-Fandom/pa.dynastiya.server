# Проверка изменений UI

Начинай с аудита кода и понятных исправлений. Достаточно проверить по одному характерному примеру каждого изменённого механизма и убедиться, что интерфейс работает как задумано. Числовые метрики, профилирование, полные обходы UI и многократные серии сравнений не являются обязательной частью работы или критерием приёмки.

## Что проверить

Проверяй то, что затронула правка: компоновку и читаемость, состояние/фокус кнопки, закрытие и повторное открытие панели, актуальность асинхронного результата. В HUD убедись, что открытая панель принимает ввод, а скрытая его не перехватывает. Общие правила проверяй на характерном компоненте, не обходя все страницы и кнопки; редактор и арсенал отдельно не проверяй без запроса.

Для запуска используй видимый изолированный профиль без кириллицы через `node mods/dynastiya/tools/resources/launch-test.cjs host` из корня workspace `pa`. Перед запуском проверь существующий профиль и назначения портов в README workspace; основной профиль игрока не используй. Подробности в `mods/dynastiya/test-profiles/README.md`.

## Когда нужна дополнительная диагностика

Точечный замер или профилировщик уместен при конкретной непонятной задержке, спорном исправлении или регрессии. Не превращай это в предварительное условие очевидной правки. Удаление нежелательного декоративного оформления выполняется по решению пользователя и не требует доказательства прироста производительности.

## Запись результата

Кратко запиши, что изменено, какой характерный пример проверен и какие ограничения остались. Обнови `changes.md` и относящуюся к исправлению карточку `optimization-reference.md`; отдельный исследовательский отчёт на каждую правку не нужен. Различай прототип и интеграцию в main клиента. Числовое ускорение без замеров не заявляй; старые исследовательские отчёты не задают обязательных требований к новой работе.
