# Ветки и выпуск версий «Династии»

Мод публикуется из `main` собственных публичных репозиториев:

| Часть | Репозиторий | Идентификатор |
|---|---|---|
| Сервер | [pa.dynastiya.server](https://github.com/Planetary-Annihilation-Fandom/pa.dynastiya.server) | `com.pa.dynastiya.server` |
| Клиент | [pa.dynastiya.client](https://github.com/Planetary-Annihilation-Fandom/pa.dynastiya.client) | `com.pa.dynastiya.client` |

Выпускай новую версию по явной команде пользователя опубликовать изменения или обновить `main`. Перед выпуском обнови `version` и `date`. После слияния PR в `main` отметь выпущенный коммит аннотированным тегом `vX.Y.Z`.

## Ветки разработки

В обоих репозиториях действует один порядок:

Рабочая ветка создаётся от `dev`. Из неё открывается PR в `dev`, а при выпуске из `dev` открывается PR в `main`.

- `main` хранит опубликованное состояние. Каталог Community Mods получает ZIP из этой ветки, поэтому отправка в `main` входит в выпуск.
- `dev` собирает готовые, но ещё не выпущенные изменения. В релиз входит весь накопленный `dev`; неготовые задачи остаются в рабочих ветках.
- Для каждой задачи веди одну рабочую ветку от актуального `dev`. Используй ветку из issue, если она указана. Все связанные изменения и правки по ревью добавляй в эту ветку. После каждого коммита сразу отправляй её в `origin`: при первой отправке выполни `git push -u origin HEAD`, затем используй `git push origin HEAD`.
- При открытии PR в `dev` или `main` запроси в GitHub ревью у всех коллабораторов-людей с правом записи, кроме автора PR. После одобрения всех этих ревьюеров и явного разрешения пользователя выполни слияние в GitHub через `Create a merge commit`.
- Перед началом задачи убедись, что её зависимости влиты в `dev` нужного репозитория.

Любое слияние веток, включая слияние в `dev` или `main`, fast-forward и синхронизацию веток, требует явного разрешения пользователя. Просьба выполнить задачу не разрешает слияние автоматически; команда «опубликуй» разрешает слияния, предусмотренные процедурой выпуска.

Технические изменения и подготовку версии веди в рабочих ветках от `dev`. После подготовки версии и до окончания выпуска согласованный состав `dev` должен оставаться стабильным, чтобы ревью и проверка относились к выпускаемым изменениям.

Тег отмечает коммит, а не ветку. Аннотированный тег `vX.Y.Z` ставится на релизный коммит в `main`; после синхронизации этот же коммит доступен из `dev`. Клиент и сервер имеют независимые номера и теги, поскольку находятся в разных репозиториях.

### Переход на `dev`

При первом переходе создай `dev` от актуального `main` и отправь её в `origin`. Существующие невыпущенные рабочие ветки направь в `dev` через PR. Уже опубликованные коммиты остаются в истории `main`.

Пример для серверной части из корня `pa` (для клиентской замени `server` на `client`):

```powershell
git -C mods/dynastiya/server fetch origin --tags
git -C mods/dynastiya/server switch main
git -C mods/dynastiya/server pull --ff-only origin main
git -C mods/dynastiya/server switch -c dev
git -C mods/dynastiya/server push -u origin dev
```

Если `dev` уже существует, используй её вместо повторного создания. Перед переключениями рабочее дерево должно быть чистым; при расхождении локальной и удалённой истории сначала разбери расхождение.

## Первое добавление в Community Mods

Для первого добавления в каталог по [инструкции автора шаблона модов](https://github.com/Quitch/New-GW-Cards/blob/main/docs/releasing.md) отправь ссылки на оба репозитория в канал `#new-mod-submissions` официального Discord PA и дождись добавления в Community Mods. Если моды уже добавлены под собственными ID, повторная заявка не нужна.

Источники ZIP для каталога:

- Сервер: `https://github.com/Planetary-Annihilation-Fandom/pa.dynastiya.server/archive/refs/heads/main.zip`.
- Клиент: `https://github.com/Planetary-Annihilation-Fandom/pa.dynastiya.client/archive/refs/heads/main.zip`.

В `modinfo.json` сохраняй собственные `identifier` и `github`, а в серверных `dependencies` и `companions` указывай `com.pa.dynastiya.client`. Зависимость устанавливает и включает клиент вместе с сервером. Поле `companions` подключает клиент при входе в игру и просмотре повтора, а `hidden: true` скрывает его из общего списка.

Серверный манифест указывает серверные части Legion Expansion, Exiles Faction и Second Wave Expansion. Клиентский манифест указывает их клиентские части. Community Mods загружает и обновляет эти моды из каталога.

Обе части используют [общие Discussions](https://github.com/Planetary-Annihilation-Fandom/pa.dynastiya.server/discussions) в поле `forum` и [GIF-аватар](https://raw.githubusercontent.com/Planetary-Annihilation-Fandom/pa.dynastiya.server/main/assets/avatar.gif) в поле `icon`. Файл аватара лежит в `assets/avatar.gif` серверного репозитория; сначала отправляй его на GitHub и проверяй raw-ссылку, затем обновляй манифесты.

## Подготовка и проверка выпуска

1. Обнови `main` и `dev` из `origin` в обоих репозиториях. Проверь, что готовые задачи и их зависимости влиты в `dev`, и определи состав выпуска для клиента и сервера. Рабочие деревья должны быть чистыми; в релиз нельзя случайно включать локальные незавершённые изменения.
2. В рабочей ветке от `dev` каждой изменённой части повысь `version` по правилам `AGENTS.md` и обнови `date`. Проверь `display_name`, `description`, `build`, ссылки и согласованность `companions`. Закоммить с описанием изменений и совместимости, сразу отправь ветку в `origin` и влей её в `dev` через PR.
3. Оставь обе части на проверяемом состоянии `dev`. Из корня `pa` запусти тестовый профиль с обычными исходниками «Династии»:

   ```powershell
   node mods/dynastiya/tools/resources/launch-test.cjs host --lobby
   ```

   В выводе должны быть собственные ID «Династии», `dynastiyaEnabled: true` и список зависимостей. В лобби проверь выбор командиров Legion и Exiles, а в матче проверь доступность построек Second Wave.
4. Проверь итоговый состав выпуска и убедись после `git fetch origin --tags`, что выбранный номер свободен. В каждом изменённом репозитории открой PR из `dev` в `main`, назначь ревьюеров и после одобрения влей его с merge-коммитом. Если содержимое изменилось после проверки, повтори затронутые проверки и запроси ревью обновлённого PR.
5. После слияния каждого релизного PR получи коммит слияния, поставь на него аннотированный тег и отправь тег в `origin`. Пример из каталога изменённого репозитория:

   ```powershell
   git fetch origin --tags
   $releaseCommit = gh pr view $releasePrNumber --json mergeCommit --jq '.mergeCommit.oid'
   git tag -a $releaseTag $releaseCommit -m "Выпуск $releaseTag"
   git push origin "refs/tags/$releaseTag"
   ```

   Здесь `$releasePrNumber` содержит номер релизного PR, а `$releaseTag` содержит тег версии, например `v1.2.0`. Если изменены обе части, согласуй их совместимость на время последовательной публикации. Синхронизируй `dev` через PR из `main`, чтобы релизный коммит вошёл в историю `dev`. Для неизменённой части выпуск не требуется.
6. После обновления каталога проверь в Community Mods собственные ID, версии, аватар и ссылку на Discussions. Push на GitHub сам по себе не подтверждает обновление каталога; точное время индексации заранее не гарантируется.

## Откат

Готовь откат в рабочей ветке от `dev` без переписывания истории: используй `git revert` нужных коммитов, отправляй ветку сразу после каждого коммита и влей результат в `dev` через PR. Для уже опубликованного изменения повысь версию и дату и проведи обычный выпуск через PR из `dev` в `main` с новым тегом. Старые теги сохраняй на исходных коммитах. Если изменения затрагивали совместимость клиента и сервера, откатывай обе части согласованно. Проверь получение исправленного выпуска через Community Mods.

Обычный выпуск отката также включает весь `dev`. Если там уже накоплены другие задачи, сначала согласуй состав исправляющего выпуска; отправлять их в `main` под видом одного отката нельзя.
