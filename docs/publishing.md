# Ветки и выпуск версий «Династии»

Мод публикуется из `main` собственных публичных репозиториев:

| Часть | Репозиторий | Идентификатор |
|---|---|---|
| Сервер | [pa.dynastiya.server](https://github.com/Planetary-Annihilation-Fandom/pa.dynastiya.server) | `com.pa.dynastiya.server` |
| Клиент | [pa.dynastiya.client](https://github.com/Planetary-Annihilation-Fandom/pa.dynastiya.client) | `com.pa.dynastiya.client` |

Выпускай новую версию только по команде пользователя «опубликуй».

## Ветки разработки

В обоих репозиториях действует один порядок:

```text
dev → рабочая ветка → dev → main + тег vX.Y.Z
                         ↑              │
                         └──────────────┘
                          синхронизация
```

- `main` хранит опубликованное состояние. Каталог Community Mods получает ZIP из этой ветки, поэтому отправка в `main` входит в выпуск.
- `dev` собирает готовые, но ещё не выпущенные изменения. В релиз входит весь накопленный `dev`; неготовые задачи остаются в рабочих ветках.
- Рабочую ветку создавай от актуального `dev`. Для задачи используй ветку из issue; готовую и проверенную работу оставляй в ней до явного разрешения пользователя на слияние. После разрешения вливай её в `dev` через `git merge --no-ff`, без пулл-реквеста. Зависимости задачи должны быть влиты в `dev` нужного репозитория, одного закрытия issue недостаточно.

Любое слияние веток, включая слияние в `dev` или `main`, fast-forward и синхронизацию веток, требует явного разрешения пользователя. Просьба выполнить задачу не разрешает слияние автоматически; команда «опубликуй» разрешает слияния, предусмотренные процедурой выпуска.

Отдельные `chore`- и релизные ветки не создаются. Технические изменения выполняются в обычной рабочей ветке, подготовка номера версии — непосредственно в `dev`. Во время подготовки выпуска не вливай туда новые задачи: проверка должна относиться к тому состоянию, которое будет опубликовано.

Тег отмечает коммит, а не ветку. Аннотированный тег `vX.Y.Z` ставится на релизный коммит в `main`; после синхронизации этот же коммит доступен из `dev`. Клиент и сервер имеют независимые номера и теги, поскольку находятся в разных репозиториях.

### Переход на `dev`

При первом переходе создай `dev` от актуального `main` и отправь её в `origin`. Существующие невыпущенные рабочие ветки влей в `dev` обычными слияниями; не переноси их в `main` до выпуска. Уже опубликованные коммиты остаются в истории `main`.

Пример для серверной части из корня `pa` (для клиентской замени `server` на `client`):

```powershell
git -C mods/dynastiya/server fetch origin --tags
git -C mods/dynastiya/server switch main
git -C mods/dynastiya/server pull --ff-only origin main
git -C mods/dynastiya/server switch -c dev
git -C mods/dynastiya/server push -u origin dev
```

Если `dev` уже существует, используй её вместо повторного создания. Перед переключениями рабочее дерево должно быть чистым; при расхождении локальной и удалённой истории сначала разбери расхождение.

## Первое добавление в Community Mods

Для первого добавления в каталог по [инструкции автора шаблона модов](https://github.com/Quitch/New-GW-Cards/blob/main/docs/releasing.md) отправь ссылки на оба репозитория в канал `#new-mod-submissions` официального Discord PA и дождись добавления в Community Mods. Если моды уже добавлены под собственными ID, повторная заявка не нужна.

Источники ZIP для каталога:

- Сервер: `https://github.com/Planetary-Annihilation-Fandom/pa.dynastiya.server/archive/refs/heads/main.zip`.
- Клиент: `https://github.com/Planetary-Annihilation-Fandom/pa.dynastiya.client/archive/refs/heads/main.zip`.

В `modinfo.json` сохраняй собственные `identifier` и `github`, а в серверных `dependencies` и `companions` указывай `com.pa.dynastiya.client`. Зависимость устанавливает и включает клиент вместе с сервером, чтобы его меню работало до подключения к матчу; `companions` подключает его при входе в игру и просмотре повтора, а клиентский `hidden: true` скрывает вспомогательную часть из общего списка.

Обе части используют [общие Discussions](https://github.com/Planetary-Annihilation-Fandom/pa.dynastiya.server/discussions) в поле `forum` и [GIF-аватар](https://raw.githubusercontent.com/Planetary-Annihilation-Fandom/pa.dynastiya.server/main/assets/avatar.gif) в поле `icon`. Файл аватара лежит в `assets/avatar.gif` серверного репозитория; сначала отправляй его на GitHub и проверяй raw-ссылку, затем обновляй манифесты.

## Подготовка и проверка выпуска

1. Обнови `main` и `dev` из `origin` в обоих репозиториях. Проверь, что готовые задачи и их зависимости влиты в `dev`, и определи состав выпуска для клиента и сервера. Рабочие деревья должны быть чистыми; в релиз нельзя случайно включать локальные незавершённые изменения.
2. В `dev` каждой изменённой части повысь `version` по правилам `AGENTS.md` и обнови `date`. Проверь `display_name`, `description`, `build`, ссылки и согласованность `companions`. Создай в `dev` релизный коммит с описанием изменений и совместимости. В рабочих ветках номера версий не повышаются.
3. Оставь обе части на проверяемом состоянии `dev`. Из корня `pa` запусти тестовый профиль с обычными исходниками «Династии»:

   ```powershell
   node mods/dynastiya/tools/resources/launch-test.cjs host --lobby
   ```

   В выводе должны быть собственные ID «Династии» и `dynastiyaEnabled: true`. Проверь загрузку обеих частей, отсутствие окна конфликтов и создание системы кнопкой `GENERATE PLANET` в разделе `LOBBY PLANET GENERATION`.
4. Просмотри итоговые изменения и убедись после `fetch --tags`, что выбранный номер ещё не занят локальным или удалённым тегом. В каждой изменённой части влей проверенный `dev` в `main` через `--no-ff`, затем поставь на полученный коммит аннотированный тег версии. Пример для сервера из корня `pa`:

   ```powershell
   git -C mods/dynastiya/server switch main
   git -C mods/dynastiya/server merge --no-ff dev -m "release: сервер <версия-сервера>"
   git -C mods/dynastiya/server tag -a v<версия-сервера> -m "Сервер <версия-сервера>: <изменения и совместимость>"
   ```

   Для клиента используй тот же порядок в его репозитории с его версией. Для неизменённой части новый тег и релизный коммит не создавай. Если при слиянии возник конфликт или изменилось проверенное содержимое, разреши его и повтори затронутые проверки до отправки.
5. Переведи `dev` на релизный коммит через fast-forward и отправь обе ветки и конкретный тег одним атомарным push:

   ```powershell
   git -C mods/dynastiya/server switch dev
   git -C mods/dynastiya/server merge --ff-only main
   git -C mods/dynastiya/server push --atomic origin main dev refs/tags/v<версия-сервера>
   ```

   Повтори для изменённой клиентской части. Сразу после выпуска `main` и `dev` указывают на один коммит, а новые рабочие ветки снова создаются от `dev`. Атомарность действует внутри одного репозитория: если изменены обе части, согласуй их совместимость на время последовательной публикации.
6. После обновления каталога проверь в Community Mods собственные ID, версии, аватар и ссылку на Discussions. Push на GitHub сам по себе не подтверждает обновление каталога; точное время индексации заранее не гарантируется.

## Откат

Готовь откат в рабочей ветке от `dev` без переписывания истории: используй `git revert` нужных коммитов и влей результат в `dev`. Для уже опубликованного изменения повысь версию и дату и проведи обычный выпуск через `dev → main` с новым тегом; старые теги не перемещай. Если изменения затрагивали совместимость клиента и сервера, откатывай обе части согласованно. Проверь получение исправленного выпуска через Community Mods.

Обычный выпуск отката также включает весь `dev`. Если там уже накоплены другие задачи, сначала согласуй состав исправляющего выпуска; отправлять их в `main` под видом одного отката нельзя.
